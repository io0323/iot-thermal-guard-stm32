# 実機フェーズの手順書

P1〜P7 では実機を使わず、ホスト版・単体テスト・仮想時間のシナリオ・契約テスト・Renode で確かめた（[docs/test-spec.md](test-spec.md)）。この書類は、**実機（Nucleo-F401RE と周辺部品）でしか確かめられないこと**を1項目ずつ書く。どれもまだ実施していない。

各項目は「何を・どの機材で・どう測るか・合格の基準・関係する書類」の形で書く。測るために計測用の変更（GPIO のトグルなど）が要る項目は、**その変更は今のコードにはなく、実機フェーズで計測用のビルドとして足す**。計測用の変更は製品のビルド（target-release）に残さない。

## 共通の機材

| 機材 | 使う項目 |
| --- | --- |
| Nucleo-F401RE（ST-LINK の仮想 COM と SWD） | すべて |
| ロジックアナライザー（4ch 以上、1MHz 以上で記録できるもの） | HW-04〜08、HW-14 |
| オシロスコープ | HW-04（PWM の波形） |
| テスター、可変抵抗または抵抗の箱 | HW-01、HW-03、HW-05 |
| 温度の基準（基準温度計、恒温槽または温度の安定した水） | HW-03 |
| デバッガ（ST-LINK＋GDB。OpenOCD または STM32CubeProgrammer） | HW-07、HW-09、HW-10、HW-12 |
| PC（iot-common-spec v0.2.1 の iotspec-contract） | HW-11 |

診断値（FR-13）は UART で返すフレームがない（共通仕様 CR-1、open-questions #1）。実機ではデバッガで `firmware_diag()` が集める値（`diag_t`、`service/diag.h`）を読む。

## HW-01 配線と、ファンを2線式にするか4線式にするか

- **何を**：[ADR-0005](adr/ADR-0005-clock-pins-peripherals.md) のピン割り当てどおりに配線し、各部品が想定どおりにつながっていること
- **配線**（ADR-0005・`bsp/stm32f4/pinmap.h`）

  | 用途 | ピン | 内容 |
  | --- | --- | --- |
  | 温度 | PA0（A0） | 3.3V → 10kΩ（1%）プルアップ → PA0 → NTC（10kΩ、B=3435）→ GND（[ADR-0001](adr/ADR-0001-circuit-assumptions.md)） |
  | ファン PWM | PA6（D12） | TIM3_CH1、25kHz。High でファンが回る向き（1000‰ で常に High）。MOSFET で駆動し、ゲートはプルアップ（HW-02） |
  | UART | PA2・PA3 | USART2、ST-LINK の仮想 COM（115200・8N1） |
  | LED 緑・黄・赤 | PA5（LD2）・PB4（D5）・PB5（D4） | High で点灯 |
  | ブザー | PB10（D6） | High で鳴る |
  | ボタン | PC13（B1） | 押すと Low（基板のプルアップ） |

- **機材**：テスター、Nucleo-F401RE
- **どう確かめるか**：電源を入れる前に導通と短絡を確かめる。25℃ 付近で PA0 の電圧が約 1.65V（生値 2048 付近）であること
- **合格の基準**：上の表のとおりつながっていて、PA0 の電圧が 25℃ の想定（生値 2048 付近）に近い
- **決めること**：ファンを2線式（MOSFET で PWM）にするか4線式（PWM 入力付き、回転数のパルスを取れる）にするか（**open-questions #6、未決**）。4線式なら回転数によるファン故障の検知を要件に足せる（基本設計書 第7章の未決事項）。ピン割り当ての最終版も実機フェーズで決める（**#7、未決**）
- **関係する書類**：ADR-0001、ADR-0005、open-questions #6・#7

## HW-02 リセット中・書き込み中にファンが回ること

- **何を**：マイコンが動いていない間（リセット中、書き込み中）もファンが回る回路であること（基本設計書 第7章「異常系の扱い」）
- **機材**：Nucleo-F401RE、ファンと MOSFET の回路、テスター
- **どう測るか**：リセットボタン（B2）を押したままにする。書き込み中（ST-LINK で書いている間）にファンを見る。PA6 は Hi-Z になり、ゲートのプルアップでオンになる
- **合格の基準**：どちらの間もファンが全開で回る。起動直後（INIT）もファンは100%（FR-12・第5章の表）
- **関係する書類**：基本設計書 第7章、ADR-0005

## HW-03 変換表を実測で置き換える

- **何を**：今の変換表は NTC の B 定数の式から作った仮のもの（[ADR-0001](adr/ADR-0001-circuit-assumptions.md)）。実際の部品と回路で測った値に置き換える。断線・短絡の生値も確かめる
- **機材**：温度の基準（基準温度計、恒温槽または温度の安定した水）、テスター、デバッガ
- **どう測るか**
  1. NTC を基準温度計と並べ、いくつかの温度（少なくとも −20・0・25・45・60・80・120℃ のうち作れる範囲）で、NTC の抵抗と ADC の生値（デバッガで DMA のバッファ、または平均した値）を記録する
  2. `tools/gen_ntc_table.py` の入力を実測値に置き換え、表を作り直す（生成器の入力だけを変える。ADR-0001 の「理由」）
  3. ADR-0001 の「影響」のとおり、生成器の検査（概算 3627・2048・238 から ±2 以内）と、故障の境界（49・50・4045・4046）・丸めの境界（237・238・3627・3628）のテストを見直す
  4. NTC を外した状態（断線）と、PA0 を GND につないだ状態（短絡）の生値を記録する
- **合格の基準**：基準温度計との差が、実機フェーズで決める精度の中にある（今の要件には精度の数値がない。ADR-0001 の「影響」）。断線で > 4045、短絡で < 50 になり、3回連続で SENSOR_FAULT になる（FR-03）
- **書類**：置き換えたら ADR-0001 を「置き換え済み」にして新しい ADR を足す
- **関係する書類**：ADR-0001、open-questions #7（変換表の実測での置き換え、**未決**）・#20・#27

## HW-04 PWM の波形、ADC の TRGO の経路と DMA の周期

- **何を**：TIM3 の PWM（25kHz、duty）、TIM2 の TRGO から ADC1 → DMA2 の経路（Renode では確かめていない。Renode は TIM2 の割り込みからのソフトウェア開始）
- **機材**：オシロスコープ、ロジックアナライザー
- **どう測るか**
  - PWM：PA6 をオシロスコープで見る。SET_FAN_OVERRIDE で 0・400・700・1000‰ を指定し、周波数と duty を測る
  - ADC・DMA：計測用のビルドで、DMA2_Stream0 の ISR の入り口で空いているピンをトグルする（ピンは HW-01 で決める）。ロジックアナライザーで間隔を測る
- **合格の基準**：PWM は 25kHz（HSI の精度 ±1% の範囲）で、duty は指定どおり（1000‰ で常に High）。DMA の半分転送・全転送の割り込みが 100ms ごとに交互に来る。`adc_take_sample` が毎回値を返し、温度が ready になる（[docs/isr-review.md](isr-review.md) の「実機フェーズで確認すること」）
- **関係する書類**：ADR-0005（周辺機能）、ADR-0006（Renode との違い）、isr-review

## HW-05 NFR-01：しきい値を超えてからファン100% まで 2.5秒以内

- **何を**：温度が crit（60.00℃）以上になってから、PWM が 1000‰（常に High）になるまでの時間（測り始めは「入力の温度が初めて crit 以上になった時刻」、open-questions #29）
- **ホストでの結果**：仮想時間のシナリオで3通り（1℃/s・10℃/s・40℃/s）とも約 1.5秒（`tests/scenario/test_scenarios.c` の NFR-01 の3件）
- **機材**：ロジックアナライザー、抵抗の箱または切り替えスイッチ付きの抵抗
- **どう測るか**
  1. NTC の代わりに、crit の少し下（例：58℃ 相当）と少し上（例：61℃ 相当）の抵抗をスイッチで切り替えられるようにする。段差は変化率の上限（5℃/100ms）より小さくする（大きいと変化率で棄却されて SENSOR_FAULT になる、FR-03）
  2. ロジックアナライザーで、ch1 にスイッチの切り替え（または PA0 の電圧の変化）、ch2 に PA6（PWM）をつなぐ
  3. 切り替えた時刻から、PA6 が常に High になる時刻までを測る。10回以上くり返す
- **合格の基準**：すべての回で 2.5秒以内（基本設計書 NFR-01。内訳：フィルタの遅れ約1秒＋継続判定1秒＋CRITICAL 確定から出力まで200ms 以内）
- **関係する書類**：基本設計書 NFR-01・第8章 決定3、open-questions #29

<a id="hw-06"></a>

## HW-06 NFR-02：制御周期 100ms のジッター ±1ms

- **何を**：task_control の周期（100ms）のずれ。ホストでは論理的に（`tests/unit/test_scheduler.c`）、Renode では仮想時間で確かめただけで、Renode は命令数の近似なのでジッターの証拠にならない（基本設計書 NFR-02）
- **機材**：ロジックアナライザー、デバッガ
- **どう測るか**
  1. 計測用のビルドで、task_control の入り口で空いているピンをトグルする
  2. UART で上位の役（契約テスト、または HEARTBEAT・CMD を送るスクリプト）を動かしながら、10分以上記録する
  3. 立ち上がりの間隔の最小・最大を求める。あわせてデバッガで診断値の `overruns`、`max_loop_cycles`、`max_task_cycles` を読む（DWT の CYCCNT、84MHz）
- **合格の基準**：すべての間隔が 99〜101ms。`overruns` が 0。各タスクの最悪実行時間の合計が 1ms（84,000 サイクル）を超えない（基本設計書 第6章「タスクと周期」の設計条件）
- **関係する書類**：基本設計書 NFR-02・第6章、詳細設計書 第2章（スケジューラ）

## HW-07 NFR-03：ISR の実行時間 各 20μs 以内、診断値の読み出し

- **何を**：SysTick・DMA2_Stream0・USART2 の各 ISR の実行時間。今は逆アセンブルの命令数からの見積もりだけ（[docs/isr-review.md](isr-review.md)：最悪 2.65μs）
- **機材**：ロジックアナライザー、デバッガ
- **どう測るか**（2つの方法のどちらか、できれば両方）
  - **DWT**：計測用のビルドで、各 ISR の入り口と出口で `DWT->CYCCNT` を読み、差の最大を静的な変数に残す。デバッガで読む（84 サイクル = 1μs）
  - **GPIO のトグル**：計測用のビルドで、ISR の入り口で空いているピンを High、出口で Low にする。ロジックアナライザーでパルスの幅を測る（トグル自体の数サイクルを含む）
  - 負荷：115200bps で途切れなく受信させる（契約テストや連続した CMD）、DMA の割り込みと重なる状態を作る
- **合格の基準**：各 ISR が 20μs（1,680 サイクル）以内。見積もり（isr-review）と大きく食い違わない。連続受信で `uart_errors`（ORE）が増えない
- **診断値**：あわせて、デバッガで `firmware_diag()` の値（受信 CRC エラー、最大ループ時間など、FR-13）が読めることを確かめる
- **関係する書類**：基本設計書 NFR-03、isr-review、ADR-0005

## HW-08 IWDG の実際の時間（LSI の個体差）

- **何を**：IWDG は LSI（公称 32kHz）÷ 32、リロード 500 で公称 500ms。LSI の個体差で 340〜940ms の幅がある（ADR-0005）
- **機材**：ロジックアナライザー、デバッガ
- **どう測るか**
  1. 計測用のビルドで、`wdt->refresh()` のたびに空いているピンをトグルする。ループを止める手段として、target-renode と同じテスト用の変数（`TG_RENODE_TEST_HOOKS=ON` で入る `g_renode_hang`）を計測用のビルドに入れ、デバッガで 1 を書く
  2. ロジックアナライザーで、最後のトグルから NRST が Low になる（ウォッチドッグのリセット）までを測る
  3. ふつうに動かした状態で長時間（1時間以上）IWDG のリセットが起きないことも見る（リセット回数が増えない）
- **合格の基準**：ループを止めると必ずリセットになる。時間が ADR-0005 の幅（340〜940ms）の中にある。ふつうの動作ではリセットが起きない（health のリフレッシュは100ms ごと）
- **関係する書類**：FR-11、ADR-0005、詳細設計書 第7章

## HW-09 リセット要因の判定（電源投入・ピン・ウォッチドッグ・ソフトウェア）

- **何を**：RCC_CSR からのリセット要因の判定（優先順は IWDG → ソフトウェア → 電源投入 → BOR → 低電力 → ピン、open-questions #51）。ホストでは純粋な関数を単体テスト（`tests/unit/test_reset_decode.c`）で確かめたが、Renode の RCC_CSR は固定値（いつも power_on）なので、実際のフラグの立ち方は確かめていない
- **機材**：デバッガ
- **どう測るか**：次の4つのリセットを起こし、起動後にデバッガで診断値の `reset_reason` と、RCC_CSR の値（RMVF で消す前。消す前の値を残す計測用の変数が要るならそれを足す）を読む

  | 起こし方 | 期待する reset_reason |
  | --- | --- |
  | USB を抜き差しする（電源投入） | power_on |
  | リセットボタン（B2）を押す | pin |
  | ループを止める（HW-08 と同じ） | watchdog |
  | デバッガから SYSRESETREQ（`monitor reset` など、ソフトウェアのリセットになるもの） | software |

- **合格の基準**：4つとも期待どおり。電源投入で PORRSTF・BORRSTF・PINRSTF がそろって立つこと（#51 の前提）も RCC_CSR の値で確かめる
- **関係する書類**：FR-12、ADR-0005（リセット要因）、open-questions #2（CR-2：リセット要因を UART で送る欄がない、**未決**）・#51

<a id="hw-10"></a>

## HW-10 `.noinit` のリセット回数

- **何を**：リセット回数は `.noinit` にマジック値と一緒に置く。電源投入（またはマジック値が壊れている）なら 0、それ以外は前回 + 1、0xFFFF で止める（ADR-0005）
- **機材**：デバッガ
- **どう測るか**：電源投入のあと、ピンのリセットを3回、ウォッチドッグのリセットを1回起こし、そのたびに診断値の `reset_count` を読む。最後に電源を入れ直す
- **合格の基準**：0 → 1 → 2 → 3 → 4 と増え、電源を入れ直すと 0 に戻る。飽和（0xFFFF）はホストの単体テスト（`test_diag.c` の `test_next_reset_count_saturates`）で確かめている
- **関係する書類**：FR-12・FR-13、ADR-0005

## HW-11 実機での契約テスト（UART）

- **何を**：iot-common-spec v0.2.1 の契約テストの7チェックを、実機の USART2（ST-LINK の仮想 COM）に対して流す。あわせて UART のボーレートの誤差と受信の取りこぼし（ORE）
- **機材**：PC、Nucleo-F401RE（仮想 COM）
- **どう測るか**

  ```sh
  uv tool install "iotspec @ git+https://github.com/io0323/iot-common-spec@v0.2.1"
  iotspec-contract --role mcu-c-01 --uart /dev/tty.usbmodemXXXX --junit hw-contract.xml   # Linux なら /dev/ttyACM0 など
  ```

  - `--uart` で既存のシリアルを開くと、契約テストは対象を起動し直せないので、**`boot_order`（起動後の最初のフレームが STATE、次の EVENT が BOOT）は「省略」になる**（iot-common-spec の `docs/contract-tests.md`。`needs_target_control`）。`boot_order` を確かめるには対象を起動し直す必要がある。方法は実機フェーズで決める（例：`--target-cmd` で基板をリセットし、仮想 COM と契約テストの pty を中継するスクリプトを用意する。Renode では `tools/renode-contract.sh` と `tools/renode_uart_relay.py` が同じ役をしている）
  - 契約テストの間、デバッガで `uart_errors`・`uart_ring_dropped`・`rx_crc_errors` を読む
- **合格の基準**：7チェックすべて合格（`boot_order` は起動し直す方法で）。`uart_errors`・`uart_ring_dropped` が 0
- **関係する書類**：FR-09・FR-10・FR-14、ADR-0006（契約テストを Renode で）、isr-review（ORE）

## HW-12 スタックの最大使用量（stack_peak）

- **何を**：起動時に塗ったスタックの残りから求める `stack_peak`（#47、#54）。見積もり（`tools/stack_report.py`）は最悪 1,560 バイト（target-release）、Renode の実行では 1,204 バイトだった
- **機材**：デバッガ
- **どう測るか**：契約テスト（HW-11）を流したあと、温度を変えて CRITICAL・SENSOR_FAULT を通したあとに、診断値の `stack_peak` を読む
- **合格の基準**：見積もりの最悪 1,560 バイトを下回り、4,096 バイトに余裕を持って収まる（NFR-04）
- **関係する書類**：NFR-04、ADR-0005（メモリ）、ADR-0006（#54 の経緯）、isr-review

<a id="hw-13"></a>

## HW-13 boot_id の雑音（再起動で変わること）

- **何を**：boot_id は内部温度センサー・VREFINT の下位ビットの雑音、DWT のサイクル数、UID、RCC_CSR を CRC-32 で混ぜて作る（詳細設計書 第7章）。Renode では UID が 0、内部温度・VREFINT は与えなければ 0 で、雑音は確かめていない。「再起動で変わる」はホスト版で確かめている（`tests/host_integration/test_reboot.py`）
- **機材**：PC（仮想 COM で STATE を読む）
- **どう測るか**：リセットボタンで20回以上起動し直し、毎回の STATE の boot_id を記録する。電源投入でも同じように記録する
- **合格の基準**：すべての boot_id が互いに異なり、0 がない（基本設計書 第6章「起動時の順序と boot_id」）
- **関係する書類**：FR-12、詳細設計書 第7章、ADR-0005（boot_id の材料）

<a id="hw-14"></a>

## HW-14 LED・ブザー・ボタンの実物

- **何を**：状態ごとの LED（点灯・1Hz・4Hz の点滅）とブザー（断続・連続）、実物のボタンのチャタリング（20ms の除去、3秒の長押し）
- **機材**：ロジックアナライザー
- **どう測るか**：LED の3ピンとブザーのピンをロジックアナライザーで記録しながら、NORMAL・WARNING・CRITICAL・SENSOR_FAULT を通す（HW-05 の抵抗の切り替えと、NTC を外す操作）。ボタンを短く押す・3秒以上押すをくり返す
- **合格の基準**：パターンが詳細設計書 第5章の表どおり。短押しの1回目で消音、2回目で承認（条件を満たすときだけ）、3秒で強制全開が切り替わる。1回の押下が2回に数えられない
- **関係する書類**：FR-07・FR-08、詳細設計書 第5章、ADR-0005（ボタンに割り込みを使わない理由）

## HW-15 Renode と実機で違う点

[ADR-0006](adr/ADR-0006-renode.md) の「Renode で確かめた範囲と、確かめていない範囲」のうち、確かめていないものと、それを確かめる項目：

| Renode で確かめていないこと | 確かめる項目 |
| --- | --- |
| ADC の TRGO の経路（target-renode は TIM2 の割り込みからのソフトウェア開始） | [HW-04](#hw-04) |

# 作品01 フェーズ P7：書類の仕上げ

## 準備

main（`a188fd6` 以降）から `phase/p7-docs` を切ること。io が `docs/prompts/` に P1〜P7 のプロンプト（`P1-prompt.md`〜`P7-prompt.md`）を置くので、未コミットならこのブランチの最初のコミットに入れる。

## はじめに読むもの

`CLAUDE.md`、`README.md`、`docs/` の全体（design・adr・isr-review・open-questions）、`.github/workflows/ci.yml`、`tests/` の構成、要件定義・基本設計書の第2・3章（FR-01〜14、NFR-01〜10）と第7章（受け入れ基準）、詳細設計書の第10章の P7 の行。読み終えたら「作るもの・作らないもの・不明点」を短く報告してから始める。

## P7 で作るもの

この作品はポートフォリオなので、**初めて読む人（採用担当のエンジニア）が、10分で「何を作り、どう確かめ、何がまだか」を正しく理解できること**を目標にする。新しい主張は書かず、リポジトリの中に根拠があることだけを書く。

1. **テスト仕様書とトレーサビリティ**：`docs/test-spec.md`
   - FR-01〜14・NFR-01〜10 の1行ずつに、それを確かめているテスト（ファイル名とテスト名、または CI のジョブと手順）を対応させる表。確かめる段（単体・ゴールデン・シナリオ・契約・pytest・品質ゲート・ターゲットのビルド・Renode）も列に入れる
   - ホストや Renode では確かめられないもの（NFR-01〜03 の実測、ISR の実行時間、実際の回路での変換表など）は「実機フェーズで確認」とし、`docs/hardware-phase.md` の該当の項目へリンクする。空欄は作らない
   - 受け入れ基準（基本設計書 第7章）のチェックリストを、どこで満たしたかのリンク付きで再掲する
2. **トレーサビリティの検査**：`tools/check_traceability.py`。①FR・NFR のすべての ID が `docs/test-spec.md` に1回以上ある ②表に書いたテスト名が `tests/` に実在する ③「実機フェーズ」のリンク先が `docs/hardware-phase.md` にある、を確かめ、CI の quality ジョブに足す
3. **実機フェーズの手順書**：`docs/hardware-phase.md`。実機で確かめることを1項目ずつ「何を・どの機材で・どう測るか・合格の基準・関係する ADR や open-questions」の形で書く。少なくとも次を含める
   - 配線（ADR-0005 のピン、NTC の分圧、ファンの駆動、LED・ブザー）と、ファンを2線式にするか4線式にするか（open-questions #6）
   - 変換表を実測で置き換える手順（ADR-0001、open-questions #7）
   - NFR-01（しきい値を超えてからファン100%まで2.5秒）、NFR-02（周期のジッター ±1ms）、NFR-03（ISR 20μs）の測り方（DWT の診断値と、GPIO のトグルをロジックアナライザで見る方法）
   - IWDG の実際の時間（LSI の個体差）、リセット要因の判定（電源投入・ピン・ウォッチドッグ・ソフトウェア）、`.noinit` の回数
   - 実機での契約テスト（`iotspec-contract --uart /dev/tty...`。`boot_order` は対象を起動し直す必要があることを書く）
   - Renode と実機で違う点（ADR-0006 の「確かめていない範囲」）
4. **README の仕上げ**：今の内容を残しつつ、冒頭を初めて読む人向けに整える
   - 冒頭の3〜5行で、何をするものか・どこまで確かめたか（ホスト・Renode・実機は未確認）
   - 構成図（Mermaid）：5層（app・service・lib・ports・bsp）と bsp_host／bsp_stm32f4 の差し替え、上位（作品03）との UART
   - 状態遷移図（Mermaid。`docs/design/02-detailed-design.md` 第4章と同じもの）
   - 検証の全体像：テストの段ごとに「何を確かめるか・件数・CI のジョブ」の表と、CI のバッジ
   - 主な数値：NFR-01 の実測（約1.5秒）、hang からの再起動、Flash・RAM・スタックの使用量、カバレッジ（いずれも PR やテストの出力にある値を使い、出典の場所を書く）
   - 書類の地図：design・adr・test-spec・hardware-phase・isr-review・open-questions・prompts がそれぞれ何か
   - 開発の進め方：設計書と CLAUDE.md をもとに Claude Code にフェーズごとのプロンプトで実装させ、仕様にないことは open-questions に記録して人が決めたこと（`docs/prompts/` へのリンク）
   - Renode の仮想時間の比が 0.7 を下回って契約テストが落ちたときの対処（MIPS を 10 から下げる。ADR-0006 にも書く）
5. **`docs/prompts/README.md`**：P1〜P7 のプロンプトの一覧（フェーズ・範囲・対応する PR の番号）と、プロンプトのあとに io が回答で決めた事項は open-questions の「決定」に記録されていることの説明
6. **`docs/adr/README.md`**：ADR-0001〜0006 の一覧が最新であることを確かめる
7. **CHANGELOG.md**：v0.1.0 として、P1〜P7 で入ったものをフェーズごとに短くまとめる。`config/version.h` の fw_version（0x0001）と対応していることを書く
8. **設計書の写しの確認**：`docs/design/` の写しに、open-questions で「決定」にした事項のうち設計書に反映すべきもの（これまでの回答で直すよう指示したもの）が入っているかを確かめ、抜けがあれば一覧にして報告する（直す前に報告すること）

## P7 で作らないもの

コードの変更（トレーサビリティの検査のスクリプトと CI の設定を除く）、新しいテスト、タグやリリースの作成（io が行う）、iot-common-spec への変更案の提出（作品01の外の作業）。

## 完了条件（すべて満たしてから PR）

1. `tools/check_traceability.py` が CI の quality ジョブで合格し、FR-01〜14・NFR-01〜10 のすべてがテストか「実機フェーズ」に対応している
2. `docs/hardware-phase.md` に上の項目がそろっている
3. README の数値と主張が、すべてリポジトリ内の根拠（テストの出力・PR・ADR）に対応している（PR の説明に、主な数値と出典の対応表を載せる）
4. README の手順を新しい環境（ubuntu:24.04 のコンテナ）で上から順に実行し、ビルド・CTest・契約テストまで通ることを確かめた（実行したコマンドと結果を PR に載せる）
5. CI の全ジョブ（host・quality・target・renode）が合格

PR の説明には、完了条件ごとの結果、設計書の写しの確認の結果、open-questions の残り（未決として残るものと、その理由：共通仕様の CR-1〜5 と実機フェーズの項目）を書く。マージはしない。

## 止まって相談すること

- テストで確かめていない FR・NFR が見つかり、「実機フェーズ」にも当てはまらないとき
- 設計書の写しに反映の抜けが見つかったとき（直す前に一覧で報告）
- README に書こうとした数値の根拠がリポジトリに見つからないとき

いずれも open-questions に記録し、その件に関わる作業を止めて報告する。
